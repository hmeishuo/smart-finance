## 二、退款規則（D16）與尚待確認事項

### 之一：D16 退款規則（已確認方向，任務 1-5 完成詳細設計，本次不實作）

- 以退款發生日認列，不回頭修改原消費月份的報表。
- 允許當月某分類的淨支出為負數，報表須清楚標示。
- 退款必須關聯原交易。
- 退款預設退回原付款帳戶；實際退入其他帳戶時，可以指定真正收到款項的帳戶。
- 原交易有多類別拆分時，部分退款必須指定各分類的沖減金額，系統不自行猜測或依比例分攤。
- 累計退款不得超過原交易的可退款金額，檢查必須能承受並行請求。1-5 評估的候選做法：鎖定原交易列（SELECT … FOR UPDATE），或在原交易上設計可檢查的累計欄位加 CHECK 限制；並行測試列入驗收。

### 之二：尚待確認

- **P2 帳務模型**：在任務 1-5 提出後，由使用者確認，目前不定案（交易種類、分錄、帳戶餘額計算、分類拆分、分期追蹤、AA 概念設計）。

## 四、權限設計（D17：方向已確認，任務 1-5 定案，目前不實作）

**更正**：使用 SQLAlchemy 連線不一定會略過 RLS。是否受 RLS 限制，取決於連線用的角色：
- superuser 或具有 BYPASSRLS 屬性的角色會略過 RLS。
- 資料表擁有者預設也會略過，除非該表設定 FORCE ROW LEVEL SECURITY。
- 其他一般角色在啟用 RLS 的表上，都受政策限制。

Supabase 內建角色（例如 postgres、service_role）的實際屬性，會在任務 1-6 用 `pg_roles` 查詢確認，不憑印象判斷。

1. **FastAPI 驗證身分**：前端用 Supabase Auth 登入後取得 access token（JWT），呼叫 API 時放在 `Authorization: Bearer` 標頭。FastAPI 在本機驗證 JWT 的簽章、exp、aud、iss；簽章金鑰優先使用專案的 JWKS 公鑰（加上快取），實作前會查證官方文件的最新做法。驗證失敗一律回 401。
2. **user_id 來源**：只取已驗證 JWT 的 `sub`。API 的 Request schema 不接受 user_id 欄位，並禁止多餘欄位。服務層的 current_user 只能從驗證依賴（dependency）取得。
3. **資料庫角色**
   - 擁有者角色：只用來執行 Alembic migration（DDL）。
   - 應用程式角色（例如 `sf_app`）：FastAPI 執行期間使用，不是 superuser，沒有 BYPASSRLS，也不是資料表擁有者，只授與需要的 SELECT／INSERT／UPDATE／DELETE 權限，不能做 DDL。
   - anon、authenticated（Supabase Data API）：前端不直接查詢資料表，所以撤銷這兩個角色對業務資料表的權限，或不給任何允許政策。
4. **分工**
   - 後端授權是主要防線：每個查詢都以 current user 過濾；修改或刪除前檢查歸屬，不屬於該使用者時回 404。
   - RLS 是第二道防線：所有業務資料表都啟用 RLS。每個資料庫交易開始時，用 `set_config('app.user_id', <uuid>, true)` 設定交易層級的值；政策的 USING 與 WITH CHECK 都要求 `user_id = current_setting('app.user_id')::uuid`。只用交易層級設定，避免連線池（pooler）把設定帶到其他請求。

### 使用者補充要求（v1.1 新增）

5. **關聯資料的歸屬一致性**
   - 除了資料列本身的 user_id，關聯的帳戶、分類、原交易（以及之後的其他關聯）都必須屬於同一使用者。
   - A 不得建立引用 B 的帳戶、分類或原交易的資料。
   - **不假設外鍵會依 RLS 檢查使用者歸屬**：PostgreSQL 的外鍵檢查不受 RLS 政策過濾，引用他人資料列仍可能通過外鍵檢查。
   - 1-5 評估的候選做法：在資料庫層用含 user_id 的複合外鍵（例如被引用表加上 `UNIQUE (user_id, id)`，引用端以 `(user_id, account_id)` 參照），讓歸屬一致性由資料庫強制；服務層同時再檢查一次，並回傳明確錯誤。
6. **使用者上下文**
   - `app.user_id` 只能由後端在驗證 JWT 之後設定，任何 API 輸入都不能影響它。
   - 缺少使用者上下文時必須拒絕存取：政策使用 `current_setting('app.user_id', true)`，未設定或空值時，政策結果為不通過（讀不到任何列，寫入被 WITH CHECK 擋下）；後端在沒有已驗證使用者時，不開啟業務資料庫交易。
7. **信任邊界與限制（1-5 正式記錄）**
   - RLS 防的是後端查詢漏寫條件等程式錯誤，不防「後端本身或 sf_app 憑證外洩」：持有 sf_app 連線的人可以自行設定 app.user_id。
   - 擁有者角色、service_role 及任何具 BYPASSRLS 的角色都不受 RLS 限制，只能用於 migration 或管理，不得給執行中的 API 使用。
   - 外鍵檢查不受 RLS 過濾，所以要靠第 5 點的歸屬一致性設計。
   - 交易層級設定依賴「每個請求都在明確的資料庫交易中執行」；連線池模式的影響在 1-6 確認。

### 隔離測試（1-10 驗收）

使用測試帳號 A、B，只在開發專案執行：
- A 讀取、修改、刪除 B 的資料 → 404，而且資料庫內容不變。
- A 的列表只出現 A 的資料。
- Request body 夾帶 user_id → 被拒絕。
- 沒有 Token、過期、偽造簽章 → 401。
- A 建立引用 B 的帳戶、分類或原交易的資料 → 被拒絕（服務層與資料庫層各自驗證）。
- 資料庫層：以 sf_app 角色、設定 app.user_id 為 A 時，查不到 B 的列；寫入 user_id 為 B 的資料會被 WITH CHECK 擋下。
- 沒有設定 app.user_id 時：查詢回傳 0 列，寫入失敗。
- **commit 後**：同一條連線的下一個交易不再保有前一個使用者的 app.user_id。
- **rollback 後**：同上，且被回滾的資料不存在。
- **交易中發生錯誤後**：連線回到連線池，下一個請求不會沿用前一個使用者的上下文。
- **連線重用**：A、B 的請求交錯使用同一個連線池（必要時將連線池大小限制為 1 來強制重用），每個請求都只看得到自己的資料。
- 以 anon key 透過 Data API 讀不到業務資料表。
- 退款並行測試：兩個同時進行的部分退款，合計超過可退款金額時，只有一個成功。

## 五、時間處理（D18：方向已確認）

- 時間點（建立時間、同步時間、排程時間）一律用 `timestamptz` 儲存，內部以 UTC 保存。
- 交易的記帳日用 `DATE` 欄位，存使用者認知的台北日期（CSV 匯入通常也只有日期）。有確切時刻時，可另外存 `timestamptz`（選用）。
- 「今天」「本月」由伺服器用 Python 標準庫的 `zoneinfo.ZoneInfo("Asia/Taipei")` 計算，不依賴主機時區（雲端主機通常是 UTC）。
- **Windows 注意**：Windows 沒有系統內建的 IANA 時區資料庫，`ZoneInfo` 需要 `tzdata` 套件才能載入 Asia/Taipei。`tzdata` 會在任務 1-3 列入後端依賴（目前不安裝），並加入測試：在 Windows 上確認 `ZoneInfo("Asia/Taipei")` 可以載入、偏移量正確。
- 期間查詢一律用半開區間 `[起, 迄)`，例如 `occurred_on >= '2026-11-01' AND occurred_on < '2026-12-01'`。對 timestamptz 的查詢，起訖點先轉成台北時間的邊界。
- 邊界測試計畫：台北時間 23:59 與 00:00 跨日、月底跨月、UTC 與台北時間不同日期的時段（台北 00:00～07:59）。
- `user_settings` 存時區，預設 Asia/Taipei。台灣沒有日光節約時間，但程式不寫死 +08:00。
- 排程以台北時間定義，部署時再換算成排程服務使用的時區。
